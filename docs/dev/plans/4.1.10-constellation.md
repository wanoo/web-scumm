# 4.1.10 « Constellation » — plan d'exécution

Programme §6. Le Bridge mono-instance devient un service durable, réplicable, isolé par tenant. Le protocole reçu par
le moteur ne change **que si** l'analyse de menace le demande (`SignalV2`), et alors avec migration.

## 1. État de départ

- `bridge/src/store.ts` : `BridgeStore` (interface synchrone : `pairing`, `player`, `playerByCapability`, `signals(playerId,
  after)`, `bySequenceKey`, `lastSequence`, `acked`, `tokenRevoked`, `revokedTokens`), `MemoryBridgeStore`,
  `JsonlBridgeStore` (journal JSONL + `JournalLock` mono-processus, `compact`, `doctor`).
- `bridge/src/bridge.ts` : `BridgeConfig`, séquence attribuée par joueur, signature JWS, SSE avec re-signature à la
  livraison (cache LRU), `trust-proxy`.
- `bridge/xcheck` (Rust) : même verdict que le JS sur Biscuit, signal, politique (`reality:xcheck --require-rust`).
- Un jeu par Bridge ; pas de `tenantId` ; pas d'OpenTelemetry ; pas de base durable.

## 2. Analyse de menace d'abord (branche 1), puis la décision `SignalV2`

Questions à instruire dans `docs/dev/threat-models/constellation.md` : un signal signé pour le tenant A peut-il être
rejoué au tenant B (même `gameId`, même `playerId` possible) ? Une capability de lecture peut-elle lire un autre
tenant ? Une clé de signature compromise sur un tenant expose-t-elle les autres ? Le `audience` d'un signal
(`WorldSignalV1.audience`?) suffit-il ?

Décision attendue (à confirmer par l'analyse) : **`SignalV2`** ajoute au contexte signé `tenantId`, `environment`
(`prod|staging|dev`), `audience` (l'origine du joueur), `gameId`, `playerId`, `sessionId`, `keyId` ; `verifySignal`
refuse un V1 quand le Bridge est multi-tenant, accepte V1 et V2 en mono-instance pendant 4.1.10 et 4.1.11, V2 seul à
partir de 4.1.12 (rupture 4.1 documentée, UPGRADING). Le simulateur et le client migrent. Test de confusion :
`tests/reality-key-confusion.test.ts` (un signal V2 du tenant A, re-présenté au tenant B avec la même clé → refusé
`audience-mismatch`).

## 3. Contrats

```ts
// bridge/src/store-async.ts (ADR 0009)
export interface RealityStore {
  appendSignal(input: ProposedSignalRow): Promise<StoredSignal>;        // transactionnel : séquence + dedupe + journal
  acknowledge(input: { tenantId; playerId; sequence }): Promise<void>;
  listAfter(cursor: { tenantId; playerId; after: number; limit: number }): Promise<StoredSignal[]>;
  rotateKeys(input: { tenantId; keyId; publicKey; retireAfter: string }): Promise<void>;
  // + les lectures de BridgeStore, toutes avec tenantId en premier argument
}
```

Implémentations : `MemoryRealityStore` (tests), `SqliteRealityStore` (`node:sqlite`, Node 22.5+ : **pas de dépendance
native**), `PostgresRealityStore` (`pg`, service container en CI ; local : Docker s'il est présent, sinon SQLite seul,
dit dans la pass sheet). Le JSONL reste outil d'import/export (`bridge migrate --from jsonl --to sqlite`).

Sémantique de livraison (D20) : « au moins une fois, application idempotente, un seul effet logique » ; la base est la
source de vérité du fan-out ; `LISTEN/NOTIFY` (Postgres) ou un poll court (SQLite) ne sert qu'au réveil des instances.

## 4. Branches, dans l'ordre

1. `docs/4110-threat-model` — le threat model, la décision `SignalV2` (ou son rejet motivé), **ADR 0009 `RealityStore`**,
   **ADR 0010 `SignalV2`** si retenu, **D20** (SQLite = local, Postgres = distribué, JSONL = migration/audit ;
   `trust-proxy` par allowlist).
2. `refactor/4110-store-interface` — `BridgeStore` devient asynchrone derrière `RealityStore` ; `MemoryRealityStore` ;
   le Bridge n'appelle plus que l'interface ; tests existants verts (`tests/bridge*.test.ts`) ; set de mutation
   `reality` mis à jour (`tools/mutation-sets.ts`).
3. `feature/4110-signal-v2` (si décidé) — `protocol.ts` : `WorldSignalV2Schema`, `signSignal({version: 2})`,
   `verifySignal` à double version avec politique ; client et simulateur ; `bridge/xcheck` Rust aligné ; vecteurs de
   test `bridge/test-vectors/signal-v2/` ; test de confusion ; UPGRADING.
4. `feature/4110-sqlite` — `node:sqlite`, schéma versionné (`migrations/0001.sql`…, avant et arrière), transactions
   pour `appendSignal` (séquence = `MAX+1` dans la même transaction, contrainte UNIQUE `(tenant, player, dedupeKey)`),
   tests de propriété (fast-check) : n propositions concurrentes → séquences contiguës, un seul signal par clé.
5. `feature/4110-postgres` — même schéma, `pg`, `LISTEN/NOTIFY` pour le réveil ; CI : service container
   `postgres:16`, job `bridge-postgres` ; les mêmes tests de propriété ; local : `docker compose` optionnel.
6. `feature/4110-tenancy` — `tenantId` partout (requêtes, index, journal, métriques, Biscuit : un bloc par tenant,
   clés et quotas distincts, rotation/révocation indépendantes) ; **tests croisant deux tenants en propriété** (toute
   lecture/écriture avec le mauvais tenant → refus) ; export et suppression d'un tenant (`bridge tenant export|delete`).
7. `feature/4110-fanout` — instances stateless : une proposition acceptée par l'instance A est livrée en SSE par
   l'instance B (réveil par `NOTIFY` / poll) ; backpressure (file bornée par connexion, 429 au-delà) ; quarantaine des
   événements invalides (table `quarantine`, `bridge doctor` les liste) ; reprise après arrêt brutal (test : `kill -9`
   d'une instance pendant 1 000 propositions, aucune perte ni doublon d'effet).
8. `feature/4110-ops` — OpenTelemetry (`@opentelemetry/api` + exporter OTLP optionnel) : ingestion, ACK, retries,
   backlog, erreurs, quarantaine, latence ; `/healthz`, `/readyz`, `/livez` ; sauvegarde/restauration (`bridge backup`,
   `bridge restore`, **rejouée dans un test**) ; procédures écrites (`docs/en/REALITY-OPS.md` : compromission,
   rotation, reprise).
9. `test/4110-load` — `tools/bridge-load.ts` : 3 instances, 1 000 joueurs, 50 000 propositions, publication de
   débit, p50/p95, limites atteintes (`docs/dev/BENCH-BRIDGE.md`), nightly.
10. `release/4.1.10` — `npm run bridge` mono-instance inchangé (profil `local`) ; SUPPORT : profils `local` (SQLite)
    et `distributed` (Postgres, `experimental` jusqu'au déploiement réel) ; `4.1.10-rc.1` avant la finale.

## 5. Critères de sortie (§6.6)

- [ ] Trois instances, un flux, aucune perte ni effet dupliqué (test de charge + test `kill -9`).
- [ ] L'arrêt brutal ne rompt pas l'ordre durable (séquences contiguës par joueur après reprise).
- [ ] Isolation des tenants testée en propriété (fast-check) et en intégration (deux tenants, Postgres).
- [ ] Sauvegarde et restauration rejouées par un test.
- [ ] `docs/dev/BENCH-BRIDGE.md` publie débit, latence, limites, machine.
- [ ] `npm run bridge` reste le profil local simple ; le JSONL s'importe.

## 6. Pièges connus

- `node:sqlite` est stable depuis Node 22.13 ; vérifier la version du runner et `engines`.
- Le set de mutation `reality` double de taille avec les stores : séparer `reality-store` (gated) de `reality`.
- Les tests Postgres n'existent pas sur la machine sans Docker : le job CI est la vérité ; la pass sheet le dit.
- La re-signature à la livraison (cache LRU) devient par tenant : clé du cache = `(tenantId, keyId, sequence)`.
- Ne jamais renommer les routes `/v1/*` : les clients 4.1.1+ les utilisent ; une v2 des routes = `/v2/*` à côté.
