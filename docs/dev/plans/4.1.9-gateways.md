# 4.1.9 « Gateways » — plan d'exécution

Programme §5. Quatre connecteurs réels (email, Telnet, SSH, Open Badges) sur un SDK commun, hors du joueur, sans
socket, secret ni code exécutable dans la PWA ou le DSL ; **tous `experimental`** dans SUPPORT tant qu'un passage réel
n'a pas eu lieu (D19).

## 1. État de départ (mesuré sur v4.1.8)

Existe :

- `bridge/src/policy.ts` : Biscuit (`grantToken`, `attenuate`, `authorize`, datalog `propose`) ; une capability par
  connecteur, atténuable, jamais élargie, révocable (`/v1/admin/revoke`, ADR 0007).
- Routes du Bridge : `POST /v1/signals` (proposition), `/v1/hooks/:id` (webhooks de démonstration, `--no-demo-webhooks`
  en production), `/v1/events` (SSE), `/v1/ack`, `/v1/pairings`, `/v1/unlink`, `/v1/keys`, `/v1/manifest`.
- `JsonlBridgeStore` avec `bySequenceKey(playerId, dedupeKey)` : une **clé de déduplication par proposition** existe
  déjà (`dedupeKey`) ; c'est la clé d'idempotence du programme, à documenter comme telle, pas à réinventer.
- `games/signals` : le jeu d'exemple Reality (cast, signaux attendus), `scripts/e2e-reality.mjs`, `npm run
  solve:reality`, `SignalSimulator` (`src/engine/reality/simulator.ts`) avec `Fault`, `SimulatedDelivery`.
- Le paquet `web-scumm-bridge` (bridge/, CLI `serve|init|doctor|compact|grant`), emballé par `scripts/pack.mjs`.

Manque : un SDK connecteur (aucune interface `RealityConnector`), un processus connecteur, les quatre connecteurs, un
paquet `web-scumm-connectors`, les tests d'abus, les threat models par connecteur.

## 2. Décisions à écrire (D19, ADR 0008)

- **D19** (DECISIONS.md) : les connecteurs sont des processus séparés du Bridge et du jeu ; leur entrée est non fiable ;
  chacun porte un Biscuit atténué à ses seuls signaux ; ils ne sont pas dans la PWA ni dans le DSL ; `experimental`
  dans SUPPORT jusqu'au passage réel (fournisseur email réel, badge réel, SSH/Telnet exposés en environnement
  contrôlé). Un jeu fonctionne sans eux (test : `dist/` du jeu ne contient aucun import de `connectors/`).
- **ADR 0008 « connector SDK »** : un connecteur reçoit, valide, normalise, associe (`tenantId` réservé pour 4.1.10 :
  champ optionnel, `'default'`), fournit `dedupeKey`, propose au Bridge avec son Biscuit ; le Bridge attribue la
  séquence et signe (inchangé). Sémantique : **au moins une fois, application idempotente, un seul effet logique**
  (jamais « exactly once »). Health, métriques (compteurs en mémoire, exposés en JSON), arrêt propre (SIGTERM →
  `stop()` → drain ≤ 5 s).

## 3. Contrats

```ts
// connectors/src/sdk.ts
export interface ConnectorContext {
  bridge: { url: string; token: string };          // Biscuit atténué du connecteur
  gameId: string;
  tenantId?: string;                               // 'default' en 4.1.9, obligatoire en 4.1.10
  limits: { maxBytes: number; maxPerMinute: number; timeoutMs: number };
  log: (event: string, fields?: Record<string, string | number | boolean>) => void; // jamais de contenu ni de secret
  propose: (signal: ProposedSignal) => Promise<ProposeResult>;
}
export interface ProposedSignal {
  source: string;                                  // 'email' | 'telnet' | 'ssh' | 'open-badge'
  kind: string;                                    // le signal déclaré par le jeu (RealityDef)
  playerId: string;
  sessionId?: string;
  dedupeKey: string;                               // idempotence : hash(source, identifiant externe)
  payload: Record<string, unknown>;                // ≤ limits.maxBytes, JSON plat, pas de HTML
  receivedAt: string;                              // ISO, horloge du connecteur (le Bridge horodate aussi)
}
export type ProposeResult = { ok: true; sequence: number; duplicate: boolean } | { ok: false; refusal: RefusalCode };
export interface RealityConnector {
  readonly id: string;
  start(ctx: ConnectorContext): Promise<void>;
  stop(): Promise<void>;
  health(): Promise<{ ok: boolean; detail: string; since: string }>;
}
```

Le Bridge accepte `dedupeKey` tel quel (déjà `bySequenceKey`) ; `duplicate: true` quand la clé existe : **test
contractuel** « la même proposition deux fois → une séquence, `duplicate` la seconde fois ».

## 4. Branches, dans l'ordre

Chaque branche : tests écrits avant le code (fixtures sous `connectors/test-vectors/<connecteur>/`), threat model dans
`docs/dev/threat-models/<connecteur>.md` **avant** le code du connecteur, docs en/fr (`docs/en/CONNECTORS.md` +
`docs/fr/CONNECTORS.md`, une section par connecteur), TOOLS pour chaque script.

0. `feature/419-cadence` — voir `plans/README.md` (fragments, mutation en deux jobs, release accélérée).
1. `feature/419-connector-sdk` — `connectors/` (paquet `web-scumm-connectors`, `connectors/package.json`,
   `scripts/pack.mjs` l'emballe : 4 archives), `sdk.ts`, `run.ts` (un processus par connecteur :
   `web-scumm-connector <id> --config <json>`), tests contractuels communs (`tests/connectors-sdk.test.ts` : propose
   deux fois, quota dépassé, payload trop gros, Biscuit refusé, arrêt propre), `games/signals` déclare un
   `connectors` block dans `RealityDef` (ids, kinds admis). CI : job `connectors` (unit + contrat). Gate :
   `fresh-install` installe la 4e archive.
2. `feature/419-email` — threat model (MIME bombs, pièces jointes récursives, HTML, en-têtes spoofés, replays
   d'un même `Message-ID`, adresse dédiée par joueur `<player>@…`) ; modes `webhook` (fournisseur : un POST signé
   HMAC, secret par config) et `imap` (dépendance `imapflow` ou équivalente : **vérifier licence MIT/ISC et
   maintenance**, `licences.allow`, `provenance.lock.json`) ; parseur MIME (`mailparser`) **dans un worker isolé**,
   profondeur ≤ 3, ≤ 256 KB texte, pièces jointes refusées par défaut ; extraction sûre (`from`, `to`, `subject`,
   `text`), HTML rendu inerte (texte seul) ; `dedupeKey = sha256('email:' + Message-ID)` ; réponses optionnelles par
   templates (`replies/*.txt`, jamais de contenu du message réinjecté sans échappement) ; rétention : messages
   supprimés après proposition acceptée (politique `keep: 0 | N jours`). Tests : 20 fixtures `.eml` dont 6 hostiles ;
   fuzzing nightly (`tools/fuzz-mime.ts`, 10 000 cas, 60 s).
3. `feature/419-telnet` — serveur séparé (`net.createServer`), **shell virtuel** : les commandes sont celles que le
   jeu déclare (`RealityDef.connectors.telnet.commands`), jamais un processus hôte ; session liée par capability (un
   code de pairing tapé au prompt) ; limites : 64 KB/s, ligne ≤ 512 octets, 100 lignes/min, session ≤ 30 min, 20
   connexions ; négociation Telnet minimale (IAC filtré) ; tests : entrées binaires, lentes (slowloris), tronquées,
   malformées, 1 000 connexions simultanées refusées proprement. `dedupeKey = sha256('telnet:' + sessionId + ':' +
   lineNo)`.
4. `feature/419-ssh` — `ssh2` (Apache-2.0, vérifier) ; authentification par clé publique déclarée ou capability
   temporaire (mot de passe = code de pairing, 3 essais) ; terminal, commandes et **système de fichiers virtuels**
   (une arborescence en mémoire par session, déclarée par le jeu) ; aucun shell, env, chemin de l'hôte ;
   redimensionnement (`pty-req`, `window-change`) ; journal expurgé ; durée ≤ 30 min ; parseur de commandes isolé ;
   tests de commandes hostiles (`../`, `$(…)`, octets nuls, 1 MB de ligne).
5. `feature/419-open-badges` — vérification OB2 (hosted + signed JWS) et OB3 (VC, JWS/Data Integrity) ; émetteur
   (allowlist d'`issuer.id`), bénéficiaire (hash salé de l'email ou `playerId`), expiration, révocation (liste de
   l'émetteur, cache ≤ 24 h) ; **réseau** : résolution DNS épinglée, allowlist d'hôtes, aucune IP privée (SSRF, DNS
   rebinding : résoudre une fois, connecter à l'IP résolue), redirections ≤ 2, JSON ≤ 64 KB, JSON-LD profondeur ≤ 8,
   délai 10 s ; résultat normalisé `valid | invalid | expired | revoked | indeterminate` ; le jeu ne reçoit jamais le
   document brut (payload = `{ badgeId, issuer, status, checkedAt }`). Tests : 12 badges fixtures (2 valides par
   format, expiré, révoqué, émetteur inconnu, signature cassée, JSON-LD récursif, redirection vers 127.0.0.1).
6. `test/419-abuse-fuzz` — un harnais commun `tools/fuzz-connectors.ts` (nightly, `continue-on-error: false` dès
   qu'il est vert deux nuits) : corpus + mutations aléatoires seedées, chaque connecteur doit répondre `refused` sans
   crash ni fuite mémoire (RSS mesuré) ; test de non-exécution : un connecteur n'a accès ni à `child_process`, ni à
   `vm`, ni à `eval` (test statique par `knip`/grep + un test runtime avec `--disallow-code-generation-from-strings`).
7. `feature/419-sample` — `games/signals` gagne un chapitre « la boîte aux lettres et le terminal » : un email
   reçu ouvre une porte, une commande tapée au terminal allume une lumière ; **replays enregistrés sans réseau**
   (`games/signals/replays/*.json`, rejoués par `npm run solve:reality` et `e2e:reality`) ; doc joueur en/fr.
8. `release/4.1.9` — SUPPORT : ligne « Connecteurs » `experimental` (4 connecteurs, CI : contrats + abus + replays ;
   humains : fournisseur réel, badge réel, SSH/Telnet exposés) ; données personnelles et rétention documentées
   (`docs/en/PRIVACY.md` + fr : quoi, où, combien de temps, comment supprimer) ; mesures vs 4.1.8.

## 5. Gates et critères de sortie (§5.8)

- [ ] Les quatre connecteurs passent le même contrat (`tests/connectors-sdk.test.ts` paramétré par connecteur) et les
      mêmes tests d'abus.
- [ ] Une livraison répétée produit un effet logique unique : test de bout en bout `e2e:reality` avec le même
      `dedupeKey` envoyé 3 fois par deux connecteurs.
- [ ] Aucun connecteur n'exécute du code arbitraire : test statique + runtime (branche 6).
- [ ] Le bundle du jeu ne contient rien de `connectors/` ni de `bridge/` (`tests/dist-no-server-code.test.ts` sur
      `dist/` : grep des chaînes `connectors/`, `ssh2`, `imapflow` absentes).
- [ ] `docs/en/PRIVACY.md` : chaque donnée personnelle, sa durée, sa suppression.
- [ ] `npm run fresh-install` installe aussi `web-scumm-connectors` et lance `web-scumm-connector --help`.

## 6. Mesures (baseline 4.1.9 vs 4.1.8)

Temps de proposition bout en bout (connecteur → Bridge → joueur) p50/p95 sur 1 000 propositions locales ; RSS d'un
connecteur après 10 000 entrées hostiles ; taille de la 4e archive ; nombre de tests ; couverture de `connectors/`
(plancher initial à poser dans `vite.config.ts` à 3 points sous la mesure).

## 7. Pièges connus

- Les dépendances réseau (IMAP, SSH) tirent des licences et des binaires : vérifier `npm run audit:deps`, pas de
  dépendance native (`node-gyp`) ; si `ssh2` exige `cpu-features` optionnel, le refuser explicitement.
- Les tests réseau locaux ouvrent des ports : ports `0` (éphémères), jamais fixes ; un test par fichier qui lance un
  serveur ; fermer dans `afterAll` ; Windows : les tests Telnet/SSH vont dans la liste d'exclusion du job `windows`
  jusqu'au portage (dire pourquoi).
- Le job `mutation` : si le set `reality` englobe `connectors/`, le temps double ; créer un set `connectors` séparé
  (`tools/mutation-sets.ts`), gated dès la branche 6.
- Ne jamais logger un payload : le test « journal sans contenu » (`grep` des fixtures dans le journal du connecteur
  après un run) fait partie des contrats.
