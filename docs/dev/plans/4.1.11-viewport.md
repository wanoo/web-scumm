# 4.1.11 « Viewport » — plan d'exécution

Programme §7. Un renderer séparé de la logique derrière une scène immuable (`SceneFrame`) ; le DOM reste l'oracle ;
**le journal sémantique appartient au cœur** (ajout du plan directeur). Parallélisable avec 4.1.9 (branches distinctes,
fichiers disjoints : `src/engine/dom/*` et `src/engine/core/*` d'un côté, `bridge/`, `connectors/` de l'autre).

## 1. État de départ

- `src/engine/dom/renderer.ts` : `SceneRenderer`, `SpriteSpec`, `LayerSpec`, `OccluderSpec`, `LightSpec`,
  `EmitterSpec`, `StageSpec` (déjà `@extension`) ; `render-dom.ts`, `render-canvas.ts` (D10, peintre Canvas depuis 3.4,
  testé par `e2e:visual --renderer=canvas`, `e2e:perf` CPU ÷4) ; `room.ts` (745 lignes) assemble la scène ; `app.ts`
  (796) est présentateur **et** renderer ; `camera.ts`, `walker.ts`, `motion.ts`, `asset-graph.ts`.
- Pas de `SceneFrame` ; les hit boxes sont calculées au rendu ; `onChange()` du moteur n'a pas de payload.
- `engine.sessions` (`SessionLog`) enregistre les entrées, pas les événements.

## 2. Décisions (ADR 0011 SceneFrame + intentions + journal sémantique ; ADR 0012 backend ; D21)

- **D21** : le rendu n'est pas une source d'état ; une intention d'entrée (`Intent`) est la seule chose qu'un renderer
  envoie au moteur ; le solveur et le replay ne dépendent d'aucun renderer.
- **ADR 0011** tranche les six propriétés : (1) la boucle de rendu appartient au renderer (`requestAnimationFrame`),
  le moteur ne connaît pas les frames ; (2) la conversion écran ↔ scène appartient au renderer, la scène est en
  coordonnées logiques 640 × 400 ; (3) les animations de présentation (marche, parole, particules) appartiennent au
  renderer, piloté par l'état logique (`actor.moving`, `speaking`) et `core/timing.ts` ; (4) les intentions sont
  produites par une couche d'entrée unique (`dom/input.ts` étendu) ; (5) l'accessibilité est appliquée par la **couche
  DOM sémantique** (boutons de hotspots, focus, clavier) synchronisée depuis le `SceneFrame`, quel que soit le peintre ;
  (6) l'invalidation : un `SceneFrame` est produit par `diff` du `GameState` (déjà `core/diff.ts`) + animation locale ;
  un renderer peut ignorer un frame identique (`frame.hash`).
- **ADR 0012** (après prototype mesuré, branche 4) : Canvas 2D reste le backend complet ; WebGL/Pixi seulement sur
  gain mesuré (fps sur `reference`, CPU ÷4, trois scènes) > 25 % **et** poids < 150 KB ; Phaser refusé sauf bénéfice
  mesuré (recouvrement avec le moteur). Un backend « null » pour les tests.

## 4. Branches, dans l'ordre

1. `feature/4111-semantic-journal` — `core/journal.ts`, émission depuis les handlers (`enter`, `gain`, `lose`, `set`,
   `ending`, `save`, `load`, session), `engine.journal` ; **tests avant** : `tests/journal.test.ts` (chaque événement,
   l'ordre, la séquence contiguë, le replay rejoue la même suite d'événements : propriété « replay(session).journal ==
   journal »), `tests/gen/random-game.ts` : 200 jeux générés, replay ⇒ même journal ; `SessionEntry.t?` ignoré
   (inchangé). Consommateurs branchés : le dev panel (liste), `tools/replay.ts` (compare), rien dans le DOM.
2. `refactor/4111-scene-frame` — `src/engine/scene/frame.ts`, `sceneFrame(state, layouts, anim)` pure ; `room.ts`
   produit un `SceneFrame` puis le peint (DOM) : **équivalence** testée par `tests/dom/scene-frame.test.ts` (le DOM
   produit avant/après identique sur `demo` et `reference`, chaque salle, 3 états) ; hit boxes précalculées dans le
   frame (polygones) ; fichier ≤ 800 lignes.
3. `refactor/4111-presenter-split` — `app.ts` ne rend plus : `Presenter` (dom/presenter.ts : overlays, menus, a11y,
   intentions) et `Renderer` (dom/render-dom.ts, render-canvas.ts) ; `App` compose ; `onIntent` ; le `Busy` owner
   (`busyCount`/`guideWait`/`skipping`, reliquat 4.1.5) devient `core/busy.ts` ; tests DOM existants verts.
4. `spike/4111-backend-measure` — prototype WebGL (Pixi 8, ESM) **sans merge** si pas de gain : mesure sur
   `reference` (`e2e:perf`, CPU ÷4, DPR 1/2/3), poids ; résultat dans `docs/dev/BENCH.md` ; ADR 0012 écrite avec les
   chiffres (branche docs).
5. `feature/4111-canvas-full` — le peintre Canvas couvre tout (décors multicouches, parallaxe, masques d'occlusion
   arbitraires (polygones), zones marchables multiples + portails (`motion.ts` : graphe de zones), caméra verticale
   et zoom, transitions, particules/éclairage 2D, restauration après `webglcontextlost`/`contextlost`) ; `e2e:visual`
   et `e2e:perf` sur DOM et Canvas ; budgets CPU/mémoire (`performance.measureUserAgentSpecificMemory` quand dispo).
6. `test/4111-equivalence` — « intentions DOM = intentions Canvas » : le même scénario e2e joué par touches/clics sur
   les deux peintres produit la même `SessionLog` et le même journal sémantique ; `prefers-reduced-motion` et
   contraste ; DPR 1, 2, 3 ; tailles mobile/desktop.
7. `feature/4111-studio-layers` — le Studio édite couches, masques d'occlusion (polygones dessinés sur la scène),
   zones/portails (onglet Rooms : vue `rooms-stage.ts`, test DOM) ; le validateur signale un masque non fermé, une
   zone sans portail.
8. `release/4.1.11` — `4.1.11-rc.1` ; budgets mobile sur émulation CPU ÷4 (téléphone réel = humain, pass sheet).

## 5. Critères de sortie (§7.6)

- [ ] `Renderer` remplaçable derrière l'interface (`null`, DOM, Canvas ; le test d'équivalence).
- [ ] Le rendu n'écrit jamais `GameState` (test statique : `src/engine/dom/render-*.ts` n'importent pas `Engine` ;
      `knip`/boundaries).
- [ ] Scènes de référence dans les budgets (CPU ÷4 : ≥ 30 fps par salle, `e2e:perf`).
- [ ] Clavier, tactile, lecteur d'écran fonctionnels (`e2e:a11y`, les deux peintres).
- [ ] Masques et couches éditables dans le Studio (test DOM + e2e:studio).
- [ ] Le journal sémantique : même suite au replay (propriété), consommé par le dev panel et `tools/replay.ts`.

## 6. Pièges connus

- `room.ts` et `app.ts` sont près de 800 lignes : chaque extraction compte les lignes (`tests/file-size.test.ts`).
- Les baselines visuelles (`tests/visual/demo/*.png`) bougent au moindre pixel : régénérer avec `--update` **et** dire
  pourquoi dans le CHANGELOG ; jamais en silence.
- `e2e:perf` sur le runner est bruyant : trois mesures, la médiane ; un budget raté une fois = relance une fois, pas un
  assouplissement.
- Le journal sémantique **n'est pas** un bus du presenter : un événement UI (menu ouvert) n'y entre pas (test qui
  refuse un `kind` inconnu).
