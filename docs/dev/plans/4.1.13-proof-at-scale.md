# 4.1.13 « Proof at Scale » — plan d'exécution

Programme §9. Promesse honnête : prouver exhaustivement une classe documentée de jeux ouverts à trois personnages dans
des budgets publiés, ou dire précisément pourquoi la preuve est incomplète. **Deux seuils** (plan directeur §5.5) :
le minimum pour sortir, l'objectif de release ; sinon la version s'appelle « Solver Research ».

## 1. État de départ

- `src/engine/tools/solve/` : `search.ts` (explicite, `solveOnce`, `solveAbstracted`, pool), `abstractions.ts`
  (propriétaire canonique, régions de mobilité, interfaces de chapitres, mémo no-op, `h32`), `expansion.ts`,
  `model.ts`, `report.ts`, `scenarios.ts` ; `solve-pool.ts` (workers) ; `.cache/proofs` (certificats par hash) ;
  `audit:corpus` (500 seeds × 3 sortes chaque nuit, 0 divergence) ; `docs/en/BENCH.md` (matrice à trois personnages
  « tronquée » depuis 3.6).
- Mesures 4.1.7 : `demo` 3 480 états (explicite 6 528), `reference` 288 états en 5,5 s ; la matrice ouverte à trois
  personnages ne termine pas.

## 2. La matrice d'abord (figée avant tout code)

`docs/dev/PROOF-MATRIX.md`, commis dans la **première** PR, et toute modification ultérieure = entrée LOG motivée :

- famille : 20 à 40 salles, trois personnages, objets transférables, puzzles croisés, dialogues, scripts, événements,
  actions destructrices et vrais softlocks, variantes ouvertes et contraintes ;
- seeds : 12 instances générées (`tests/gen/random-game.ts` étendu : paramètre `characters: 3`, `rooms: 20..40`),
  seeds listées ;
- budgets : états (10 M), temps (20 min par instance sur le runner `ubuntu-24.04`, 10 min sur le Mac du mainteneur,
  les deux publiés), mémoire (4 GB) ; verdict attendu par instance (`proved` / `softlock:<chemin>`) établi par
  l'exhaustif de référence là où il termine, `unknown` sinon ;
- la machine de mesure nommée (runner + Mac), la commande exacte (`npm run prove:matrix`).

## 3. Décisions (ADR 0015 représentation compacte ; backend symbolique sur gain mesuré seulement)

- **Représentation compacte** : `GameState` encodé en bitsets (flags, inventaires, états finis) + interning des
  positions ; hash incrémental (xxhash 64 ou FNV-1a 64 sur le bitset) ; transitions compactes (verbe, cible, delta) ;
  parents et témoins compressés (parent = index 32 bits) ; stockage disque optionnel (`.cache/proofs/<hash>/visited.bin`) ;
  checkpoint toutes les N minutes et reprise (`--resume`).
- **Dominance** différentielle : inventaire ⊇ et ressources monotones ⇒ état dominé ignoré ; normalisation des
  personnages/objets équivalents (symétries déclarées ou détectées) ; décomposition des sous-puzzles indépendants ;
  frontières d'objectifs/chapitres (existe : `chapters.ts`). **Chaque règle** est comparée à l'exhaustif sur les
  petits jeux générés ; une règle qui change un verdict est **désactivée en mode preuve** (le profil le dit).
- **Backend symbolique** (`spike/4113-symbolic`) : BDD (`@…/bdd` ou implémentation maison), SAT/SMT (z3 wasm), recherche
  bidirectionnelle, CEGAR ; gardé seulement si gain mesuré sur la matrice **avec témoin lisible** ; sinon le résultat
  va dans BENCH.md et le spike n'est pas mergé.
- **Parallélisme** : partition par hash d'état, work stealing, table de visites partagée (`SharedArrayBuffer` dans
  les workers Node) ou shardée ; résultat **déterministe indépendant du nombre de workers** (test : 1, 2, 4 workers →
  même verdict, même témoin minimal).

## 4. Branches, dans l'ordre

1. `docs/4113-matrix` — PROOF-MATRIX.md, les 12 seeds, les verdicts de référence (ou `unknown`), les budgets, ADR 0015.
2. `feature/4113-explosion-profile` — `solve --profile` : états attribués aux dimensions (positions, inventaires,
   flags, dialogues, scripts, symétries, no-ops, permutations) ; `docs/dev/PROOF-PROFILE.md` par instance ; le rapport
   dit quelle abstraction est active et pourquoi.
3. `refactor/4113-compact-state` — bitsets + interning + hash incrémental + transitions compactes ; **oracle** : sur
   `demo`, `reference`, 200 jeux générés, même ensemble d'états atteignables et même verdict que l'implémentation
   actuelle (test différentiel) ; mémoire et temps mesurés avant/après (BENCH.md).
4. `feature/4113-checkpoint` — checkpoint/reprise ; test : tuer le solveur à 30 %, reprendre, même verdict et même
   témoin ; `truncated` jamais `proved` quand un budget coupe (test).
5. `feature/4113-dominance` — règles de dominance et symétries, **différentielles** (chaque règle on/off comparée à
   l'exhaustif sur les petits jeux ; désactivée en preuve si un verdict change) ; décomposition par sous-puzzles.
6. `spike/4113-symbolic` — pas de merge sans gain ; résultat chiffré dans BENCH.md.
7. `feature/4113-partition-workers` — partition + work stealing + visites partagées ; déterminisme 1/2/4 workers ;
   `solve-pool.ts` étendu.
8. `release/4.1.13` — nom selon les seuils (§5) ; `prove:matrix` en nightly (pas en CI de PR) ; mesures.

## 5. Les deux seuils (décision de nommage de la release)

- **Minimum pour sortir** : gain significatif mesuré vs 4.1.12 sur la matrice (états/s × 3 ou mémoire ÷ 3, les deux
  publiés) ; représentation compacte livrée ; checkpoint/reprise ; verdict identique à l'exhaustif sur les petits jeux
  (0 divergence sur 500 seeds) ; aucune fausse preuve (`truncated` jamais `proved`).
- **Objectif de release** : les 12 instances de la matrice terminent dans leur budget avec un verdict.
- Minimum atteint, objectif non : la release s'appelle **« Solver Research »** avec le rapport d'écart (quelles
  instances, quel budget, quelle dimension explose). Minimum non atteint : pas de release, le travail reste en branche.

## 6. Critères de sortie (§9.8, lus avec les seuils)

- [ ] Petites variantes : exactement le verdict de l'exhaustif (différentiel, 500 seeds).
- [ ] La matrice termine sous budget (objectif) ou l'écart est publié (Solver Research).
- [ ] Chaque softlock a un chemin minimal reproductible (témoin rejoué par `replay`).
- [ ] Le profil expose les abstractions actives.
- [ ] Une limite produit `truncated`, jamais `proved`.
- [ ] Reprise d'une recherche interrompue ; même verdict à 1 ou N workers.

## 7. Pièges connus

- Les benchmarks sur le runner GitHub varient de 20 % : publier médiane de 3, et le Mac à côté.
- `SharedArrayBuffer` dans vitest : activer `--pool=threads` pour ces tests seulement (config séparée).
- Un witness compressé doit rester **rejouable** par `tools/replay.ts` : test systématique.
- Ne pas laisser `search.ts` dépasser 800 lignes : `search/compact.ts`, `search/dominance.ts`, `search/partition.ts`.
